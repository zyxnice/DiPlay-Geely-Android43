# 吉利星越 2019 款 8600 USB 问题与验收清单

整理日期：2026-10-29。计划于当天（北京时间）下班后开始实车验证，具体开始时间以用户现场通知为准。本文是后续 USB 优化与验证的统一入口；整理文档不代表已经开始车测或通过验收。

## 1. 范围、基线与判定口径

- 仅适用于吉利星越 2019 款 8600 原厂车机；已记录环境为 GEELY NL5QJ / C3ALFUS、Android 4.3 / API18、固件 `06.03.08600.H53.00060`，现场仍须核对实际值。
- 以 USB3-B-output1 为已归档的体验对照：保住已改善的音乐与跟手，优先解决画面连续性。现场实际安装包与归档基线分别记录，不假定当前车机仍安装 output1。
- output2 曾获画面更连续、跟手较弱的反馈；后续候选不因构建通过、策略触发或模拟测试通过就视为改善。每版先记录用户原话，再结合日志分析。
- 下文连接耗时、重复次数、播报次数和测试时长均为**暂定值，现场开始前确认，可调整**。通话/Siri 暂列必验项；若当晚无法完成，标未测并留待补验。
- 各项结论仅使用“通过／未通过／未测”。历史样本用于说明背景，不提前填入本轮通过结果。
- HUD 和无线均不属于本轮 USB 验收；USB 方案验收通过后优先推进 HUD 适配，无线连接保留为后续规划。

## 3. 必须补齐的验收项

以下属于证据不足、需要验证的项目，不直接认定为已知故障。

| 编号 | 项目 | 检查方法（数量和时长暂定） | 通过标准 |
| --- | --- | --- | --- |
| USB-05 | 连接及恢复 | 软件断开重连 3 次、物理拔插 3 次、正常关车再启动 2 次。 | 均可通过正常入口恢复，不依赖 ADB 命令、手工切 USB 模式、解绑驱动或卸载清数据。额外手动重试必须记录；不能将物理重插算作软件恢复成功。 |
| USB-06 | 音乐与导航声音 | 缓存音乐连续播放，穿插至少 5 次导航播报。 | 无可感知断音、爆音、明显延迟或音量异常；导航声音正常叠加或切换，结束后音乐恢复；不弱于 output1 已有音乐体验。 |
| USB-07 | 通话、Siri 与返回 | 来电、去电、Siri 各验证一次。 | 麦克风、扬声器及声音路由正常；结束后音乐、画面、触控恢复。未执行的分项不得默认通过。 |
| USB-08 | 清晰度与显示比例 | 对照静止文字、地图细节、屏幕边缘和触点位置；必要时保存系统原始截图与屏幕照片。 | 无明显拉伸、裁切、二次缩放模糊或触点偏移；用户确认清晰度可接受。1920×720 协商值本身不是验收结果。 |
| USB-09 | 连续运行及页面恢复 | 先做 10 分钟短测，通过后做 30 分钟混合使用；切换原车页面再返回。 | 无应用崩溃、持续黑屏、连接失效、明显音画退化或延迟持续累积；返回后画面、触控、声音正常。 |

## 4. 今晚验证顺序

1. 用户停车并通知开始后，核对车机、手机、实际安装 APK、设置和回退包；确认本文暂定阈值、次数及必验项。
2. 先测现场当前版本，记录完整进入耗时、音乐、画面、跟手与清晰度；与 output1 的已知体验分开记录。需要重新安装对照包时，先核对同包名、同签名及设置保留情况。
3. 优先检查 USB-01、USB-02 和音乐不退化。若使用诊断候选，只按证据判断，不承诺诊断包直接改善体验。
4. 通过短场景后，按 USB-03～USB-08 检查启动、授权、恢复、声音和显示；同一次测试可覆盖多项，不重复折腾设备。
5. 执行 USB-09 短测；通过后再长测。需物理拔插、正常关车再启动、电话或 Siri 的步骤由现场按顺序配合。
6. 每版先记录用户分项原话与异常，再汇总日志。明显退化时保存证据、恢复已核验的可用版本；不为凑齐清单继续保留退化包。
7. 当晚未完成的项目保持未测，记录下一步；不得把短测完成写成 USB 全部验收通过。

本轮准备不包含现在连接车机、安装新包或修改车机配置。下班后的实际操作以现场通知和当时确认的范围为准。

## 5. 测试条件与计时规则

- 对照保持同一手机、线缆、USB 接口、音乐和操作场景；显示分辨率、请求帧率、缓冲和性能开关记录实际值，改变变量必须注明。
- 候选按 APK 文件名与 SHA-256 识别，不能仅凭共用版本号或桌面图标判断；设备上实际安装身份需核验。
- 常规连接在手机已解锁、线已接好、车机可操作的条件下，从正常应用入口操作开始，包含应用内部准备至首帧的全部等待。应用已打开时单独标“连接按钮场景”，不与首次打开混算。
- 冷启动分别记录“关车再启动至系统可操作”和“从正常应用入口至首帧”；后者暂以 30 秒为目标，不能排除应用自身启动等待。手机未就绪等外部等待单列，不悄悄扣除失败样本。
- 日志另记录应用入口→控制器→USB 就绪→媒体连接→首帧。日志首帧若仅为 Surface 提交，不等于物理屏幕已亮起；用户看到首帧的记录单列。
- 不强制请求 60fps 作为通过条件；应用接收/提交帧率不等于物理屏幕帧率。静止画面低帧或停发窗口不得直接当作动态卡顿证据。
- 听感、跟手、连续性、清晰度分别评价。零错误日志不能代替用户体验确认，也不能推断未经覆盖的通话、冷启动或长时间稳定性。
