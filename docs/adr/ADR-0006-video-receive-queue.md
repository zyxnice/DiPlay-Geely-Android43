# ADR-0006：8600 C 迭代采用有界视频接收队列

状态：Accepted（用户授权实施；实车收益待验收）

日期：2026-10-28

作者：Codex

最后修改：2026-10-28

## 上下文

B原生媒体解密已由实车日志证实生效，用户确认音乐明显改善，画面仍不够流畅。
当前视频TCP读取、解密和交付在同一线程，调用耗时与调度会阻塞继续读包。
尚无证据认定它是剩余卡顿的唯一原因；按既定A/B/C方案做可回退对照。

## 决策

沿用API18 Kotlin/Java、既有原生解密和MediaCodec。C将完整包读入与顺序解密分为两个工作线程；
队列同时限制条数、字节、等待时间及帧龄，nonce在读取时分配，配置消息保序。
接收侧失链通过MediaSink默认回调送到同一解码队列；原始接收时间随帧传递，避免两个队列各自重置延迟预算。
接收队列预算为10条/4MiB、等待最多30ms、视频帧龄250ms；另有reader与worker各一个在途包，
最大协议包仍8MiB，解密明文和native临时副本另占内存。C解码队列以4MiB共同约束帧与配置，
最多10帧、2个配置、1个Surface和1个失链标记。实车heapgrowthlimit=64m，因此不采用10个任意大帧；
队列上限仍不是整个进程内存上限，实际峰值和GC须实车观察。

C首包默认开启队列、关闭软恢复。可选软恢复仅在已正常输出且格式/Surface未变时保留实例等待IDR，
旧输出不显示；新IDR已提交仍无输出则有界回退重建并禁用本会话软恢复。其它错误继续重建。
不实现flush、全局USB网络替换或更改音频。普通及A/B构建不启用C策略。

## 后果

正面：隔离读取与解密的短时抖动；内存、延迟和参考链丢失有明确边界；能独立对照队列与恢复。
负面：增加工作线程及缓冲，不能解决手机产帧、USB链路或平台调度的所有问题；有并发、nonce及旧帧污染风险，
必须验证关闭顺序、认证失败和恢复路径。软恢复在API18硬件解码器上仍需实测。

## 替代方案

- 保持B同步路径：作为开关关闭/同签覆盖回退保留，不提供接收解耦对照。
- 无界队列或放宽到800ms：可能让触控越来越慢并增加内存，未采用。
- 一律flush或一律保留解码器：首帧/CSD/Surface及硬件错误条件不同，未采用；flush仅在后续证据满足原计划条件时另试。
- 整体替换USB网络栈：影响范围和归因成本过大，不属于本轮。

## 撤销条件

出现认证回归、关闭后旧帧、不可控内存/延迟、黑屏花屏、音乐恶化或没有明确收益时，关闭C策略或覆盖回B修复包。
默认USB关联修复保持，不用手工改系统USB配置补救性能候选。
