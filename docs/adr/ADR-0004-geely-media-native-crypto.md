# ADR-0004：8600 B 迭代采用可回退的原生媒体认证解密

状态：Accepted（用户授权制作 A/B 包；API 18 加载及实车流畅度待验收）

日期：2026-10-27

作者：Codex

最后修改：2026-10-27

## 上下文

USB2 已由用户确认进入 CarPlay，但画面和音乐仍卡顿。当前接收循环使用 BouncyCastle Java
实现 ChaCha20-Poly1305；没有现场分阶段耗时足以确认其为唯一瓶颈。Legacy 的
`bec397e2a3bbf85a4ff3128be68dd2fcc810d18f` 提供 C 实现及 JNI；其原地修改输入的契约
与当前公共 `AirPlayCrypto.chachaOpen` 不同，且该公共方法也用于配对和控制通道。

## 决策

在原 `airplay` 模块添加 `MediaFrameCrypto`，由音频/视频流各自拥有实例和累计计数。
只有 B 迭代启用 native，A 不编译打包 `xcertplay_chacha`；JNI 不改变输入，只把通过
Poly1305 校验的明文写入单独输出。移植 C 实现保留来源和 GPL-3.0 标识，使用现有 NDK
构建入口；不复制 Legacy 的 API 19 参数，也不更换整个 USB/网络或解码器实现。

`NativeChaCha` 首次使用才加载库并运行 RFC 8439 正向/篡改拒绝自检。库不可加载或自检
失败时回退既有 Java 实现；标签失败直接拒绝，不能作为普通可用性失败重试。JNI 使用
`GetByteArrayElements`，不在大帧运算期间持有 `PrimitiveArrayCritical`；VM 仍可能复制，
因此不承诺零拷贝。

配对、控制和 IAP 隧道继续使用原 `AirPlayCrypto.chachaOpen`。媒体入口仍保持输入不变、
输出和错误语义一致。每流的路径、回退、认证失败和耗时累计交给既有五秒诊断输出，
首个 native 调用包括一次性载入/自检成本，比较使用预热后的窗口。

## 后果

正面：可单独验证媒体密码运算开销，不扩大配对/control 风险；A 与 B 有明确可对照构建；
native 无法加载时保持连接能力。

负面：增加一份原生代码及 ABI 维护；Java fallback 必须保留；API 18 的符号/加载和音画收益
仍须真机验证。回退成功不等于 B 性能验收通过，首次调用耗时不可当作稳定吞吐。

## 替代方案

- 直接替换公共 `chachaOpen`：影响配对及控制，超出本轮媒体性能范围，不选。
- 保留全 Java、只调线程：风险较小但不能验证密码运算瓶颈；作为 A 对照及 B fallback 保留。
- 直接复制 Legacy 的原地解密：修改调用方输入所有权，不选。
- 禁用认证或自创简化算法：破坏协议完整性，不选。

## 撤销条件

若 native 在 API 18 加载失败、自检失败、认证行为不一致、音视频变差或没有可重复收益，
回到 A 或关闭 native 的同签名构建。保留 Java 回退直到有足够 ABI/实车覆盖证明可移除；
本次不安排删除。若以后扩展到控制通道，必须重新核查所有调用方并记录决策。
